# Flutter Release and CI Standards

Everything that decides *which app* a build produces and *whether that build is allowed to
exist*: the two flavor switches, the native per-flavor identity, the pinned toolchain, the
pull-request gate, the canonical `analysis_options.yaml`, CI-generated versioning, and the
release job that obfuscates and uploads symbols.

**Scope boundaries.** This layer owns the **configuration files** — workflow YAML, Gradle
build files, the Android manifest, iOS plists and `project.pbxproj`, per-flavor `.env_*`
files, and `analysis_options.yaml`. It does not own **credentials and store accounts** —
keystores, provisioning profiles, App Store Connect API keys and the submission checklist are
the `/flutter-signing` command. It does not own **build-failure diagnosis** — "Gradle says
duplicate class", "CocoaPods can't find a spec", "the archive step hangs" is
`/flutter-build-doctor`. The `AppLogger`, the crash reporter and the analytics catalogue are
`logging/flutter-observability`; this layer says only *what values* get set as crash keys and
*where* the bootstrap assertion goes. Deep-link `.well-known` files, which are also per-flavor,
are `frontend/go-router`.

Sections are independent. Read the one you need.

The flavor set used throughout is `dev`, `staging`, `prod`. Three is the working minimum:
a local/emulator target, a target QA installs from the store's test track, and production.
Pick the names once and use the same three strings in Gradle, in Xcode, in the `.env_*`
filenames, in `--dart-define`, and as the `flavor` crash key value.

## 1. Two flavor switches, not one

**Rule: every build and run command passes both `--flavor <name>` and
`--dart-define=FLAVOR=<name>`. They are independent switches, and setting one does not set
the other.**

This is the reason this layer exists. The two switches are spelled similarly, appear in the
same command, and carry the same word, so they read as one option written twice. They are not.

| Switch | Consumed by | Selects |
|---|---|---|
| `--flavor prod` | Gradle product flavor / Xcode scheme + build configuration | `applicationId`, bundle id, launcher icon, display name, signing config, `google-services.json`, entitlements |
| `--dart-define=FLAVOR=prod` | The Dart compiler's environment | Everything `String.fromEnvironment` reads — API base URL, identity pool id, analytics property, log level |

Neither one can see the other. Gradle has no idea what you passed to `--dart-define`; the Dart
compiler has no idea which product flavor was selected. There is no cross-check anywhere in
the toolchain, and no warning.

```bash
# ✅ both switches, same value
flutter build appbundle --release \
  --flavor prod \
  --dart-define=FLAVOR=prod

# ❌ ships a binary with the production application id, production icon and production
#    signing — talking to the dev API with the dev identity pool
flutter build appbundle --release --flavor prod
```

**What the second command actually produces.** The store listing is right. The icon is right.
The app id is right, so it upgrades the real production install. It is signed with the release
key. It passes review. And every request goes to the dev backend, every sign-in mints a token
in the dev user pool, and every crash is filed under the dev crash-reporter property. Nothing
about the build output looks wrong, because nothing about it *is* wrong on the native side.
The Dart side simply never learned which app this was.

**Rule: the pairing is enforced in exactly one place — a CI-only build script or composite
action — and hand-typed nowhere else.** A rule that says "remember to pass both" is a rule
that survives until the first hotfix at 23:00.

```yaml
# .github/workflows/_build.yml — one reusable workflow, called by release and by nightly
inputs:
  flavor:
    required: true
    type: string
steps:
  - name: Build Android App Bundle
    run: |
      flutter build appbundle --release \
        --flavor ${{ inputs.flavor }} \
        --dart-define=FLAVOR=${{ inputs.flavor }} \
        --dart-define-from-file=.env_${{ inputs.flavor }} \
        --obfuscate \
        --split-debug-info=build/symbols/${{ inputs.flavor }}
```

One input, used four times. There is no way to call this workflow with the two switches
disagreeing.

**`--dart-define-from-file` does not replace `--dart-define=FLAVOR=`.** The file supplies the
per-flavor *values*; `FLAVOR` is the *name of the selection*, and putting it inside the file
means a file mix-up is undetectable — a file named `.env_prod` containing `FLAVOR=dev` is
valid input. Keep `FLAVOR` on the command line, next to `--flavor`, where the two are one line
apart and a mismatch is visible in review.

## 2. Resolving the flavor in Dart: no fallback, fail the build

**Rule: `const String.fromEnvironment('FLAVOR')` is read with no fallback value, and an empty
result throws before `runApp`.**

`String.fromEnvironment` returns the empty string when the define is absent — it does not
throw, does not warn, and is resolved at *compile* time, so there is no runtime signal that
anything was missing. Give it a fallback and you have written the bug: a release built without
the define compiles cleanly, boots cleanly, and runs as whatever the fallback said.

```dart
// lib/core/env/app_flavor.dart

enum AppFlavor {
  dev,
  staging,
  prod;

  static const _raw = String.fromEnvironment('FLAVOR');

  /// Resolved at compile time from --dart-define=FLAVOR=<name>.
  /// Throws when the define is absent, so a misconfigured build cannot boot.
  static AppFlavor resolve() {
    if (_raw.isEmpty) {
      throw StateError(
        'FLAVOR was not defined. Every build must pass '
        '--dart-define=FLAVOR=<dev|staging|prod> alongside --flavor.',
      );
    }
    return AppFlavor.values.firstWhere(
      (f) => f.name == _raw,
      orElse: () => throw StateError('Unknown FLAVOR "$_raw".'),
    );
  }

  bool get isProduction => this == AppFlavor.prod;
}
```

Three properties of this that matter:

- **No fallback in the `fromEnvironment` call.** The failure is loud and immediate.
- **The unknown value also throws.** `FLAVOR=produciton` is a typo in a workflow file, and
  falling back to dev on an unrecognised name reintroduces the exact bug.
- **`enum`, not `String`.** Downstream code switches on the enum, so adding a flavor is a
  compile error at every decision point rather than a missed `if`.

**Rule: every other environment value is read once, in one class, and is non-nullable.**

```dart
// lib/core/env/app_environment.dart

final class AppEnvironment {
  const AppEnvironment._({
    required this.flavor,
    required this.apiBaseUrl,
    required this.identityPoolId,
  });

  final AppFlavor flavor;
  final Uri apiBaseUrl;
  final String identityPoolId;

  static AppEnvironment resolve() {
    final flavor = AppFlavor.resolve();
    return AppEnvironment._(
      flavor: flavor,
      apiBaseUrl: Uri.parse(_required('API_BASE_URL', flavor)),
      identityPoolId: _required('IDENTITY_POOL_ID', flavor),
    );
  }

  static String _required(String key, AppFlavor flavor) {
    final value = switch (key) {
      'API_BASE_URL' => const String.fromEnvironment('API_BASE_URL'),
      'IDENTITY_POOL_ID' => const String.fromEnvironment('IDENTITY_POOL_ID'),
      _ => '',
    };
    if (value.isEmpty) {
      throw StateError('$key missing — check .env_${flavor.name} in CI.');
    }
    return value;
  }
}
```

The `switch` is required, not stylistic: `String.fromEnvironment` takes a **const** key, so a
loop over a list of names does not compile. Enumerate the keys explicitly. It is a short list,
and the compiler now proves that every key the app reads is a key someone declared.

**Never `Platform.environment`.** It reads the *device's* process environment, which on a
phone is empty. It compiles, it returns nothing, and it is a different mechanism entirely.

**Never a flavor read from an asset file bundled at runtime.** An asset can be swapped in a
repackaged APK, and it moves the failure from build time to first launch on a user's device.

## 3. Startup assertion, the one log line, and the crash keys

**Rule: bootstrap resolves the environment, asserts it, logs one line naming the flavor and
the API host, and sets both as crash keys — before the first frame.**

The failure this catches is the one the previous two sections cannot: a build where both
switches were passed, both agree, and the `.env_prod` file that CI wrote happens to contain
the staging host. Nothing upstream can see that. The startup line can.

```dart
// lib/main.dart
Future<void> main() async {
  runZonedGuarded(() async {
    WidgetsFlutterBinding.ensureInitialized();

    final env = AppEnvironment.resolve();          // throws on a missing define (§2)
    assert(_flavorMatchesHost(env), 'FLAVOR=${env.flavor.name} but API host is '
        '${env.apiBaseUrl.host} — the env file and the flavor disagree.');

    final logger = buildLogger(env);
    logger.info('app.start', fields: {
      'flavor': env.flavor.name,
      'api_host': env.apiBaseUrl.host,
      'version': packageInfo.version,
      'build': packageInfo.buildNumber,
    });

    await reporter.setCustomKey('flavor', env.flavor.name);
    await reporter.setCustomKey('api_host', env.apiBaseUrl.host);
    await reporter.setCustomKey('app_version', packageInfo.version);
    await reporter.setCustomKey('build_number', packageInfo.buildNumber);

    runApp(ProviderScope(child: App(env: env)));
  }, reporter.recordFatal);
}
```

| Signal | Where it is read | What it catches |
|---|---|---|
| `assert` | Debug and profile only, first run on a dev machine | Flavor/host disagreement before it reaches a build server |
| `app.start` log line | Device log, and the log sink in staging | "Which build is on this phone?" — answered in one line, without a rebuild |
| `flavor` + `api_host` crash keys | Every crash report | A production-property crash report whose `api_host` is a dev host is the smoking gun |

The `flavor` crash key is what lets you route alerts: staging crashes must not page anyone.
See `logging/flutter-observability` for the logger and reporter contracts — this layer only
fixes *which* keys are set and *when*.

**Rule: the assertion is an `assert`, not an `if`/`throw`, and the check itself is a
whitelist.** An `assert` is compiled out of release, which is what you want here — this is a
developer-machine tripwire, not a runtime kill switch. The build-time throw in §2 is the
release-side protection.

```dart
bool _flavorMatchesHost(AppEnvironment env) => switch (env.flavor) {
  AppFlavor.prod => env.apiBaseUrl.host == 'api.example.com',
  AppFlavor.staging => env.apiBaseUrl.host == 'api.staging.example.com',
  AppFlavor.dev => true,   // dev points at whatever the developer is running
};
```

**Never log the full API base URL** — the path or query can carry a tenant or a key. Log
`.host`. This is the same rule as `redactUri` in `logging/flutter-observability`.

**Rule: the flavor is visible in the running app, not just in the log.** A debug banner, a
suffix on the app bar title, or a coloured status bar for every non-production flavor. QA
reporting "it's broken on prod" while running staging costs more triage time than the banner
costs to write.

```dart
// Only the production flavor is unmarked.
if (!env.flavor.isProduction) {
  return Banner(
    message: env.flavor.name.toUpperCase(),
    location: BannerLocation.topEnd,
    child: child,
  );
}
```

## 4. Android flavors: id suffix, display name, icon

**Rule: every non-production flavor carries an `applicationIdSuffix`, its own `app_name`
string resource, and its own launcher icon.**

Without the suffix there is one application id, so installing the QA build *replaces*
production on the device. The tester loses their production session, their local database and
their draft data, and — the part that actually costs a release — cannot compare the two builds
side by side. With the same name and icon, two installed builds are indistinguishable on the
home screen, and every bug report becomes "which one were you in?".

```kotlin
// android/app/build.gradle.kts

android {
    namespace = "com.example.app"
    compileSdk = 35
    ndkVersion = "27.0.12077973"

    defaultConfig {
        applicationId = "com.example.app"
        minSdk = 24
        targetSdk = 35
        // versionCode / versionName come from CI — see §10
        versionCode = (project.findProperty("versionCode") as String).toInt()
        versionName = project.findProperty("versionName") as String
    }

    flavorDimensions += "env"

    productFlavors {
        create("dev") {
            dimension = "env"
            applicationIdSuffix = ".dev"
            versionNameSuffix = "-dev"
            resValue("string", "app_name", "Example Dev")
        }
        create("staging") {
            dimension = "env"
            applicationIdSuffix = ".staging"
            versionNameSuffix = "-staging"
            resValue("string", "app_name", "Example QA")
        }
        create("prod") {
            dimension = "env"
            // no suffix: this is the real application id
            resValue("string", "app_name", "Example")
        }
    }
}
```

**Rule: the manifest reads the string resource; it never hardcodes the label.**

```xml
<!-- android/app/src/main/AndroidManifest.xml -->
<application
    android:label="@string/app_name"
    android:icon="@mipmap/ic_launcher">
```

A literal `android:label="Example"` in the shared manifest silently wins over every
`resValue`, and the flavors all end up named the same. If you see the label as a literal, that
is the bug.

**Icons are per-flavor source sets, not a runtime overlay.**

```
android/app/src/dev/res/mipmap-*/ic_launcher.png        # e.g. a red band
android/app/src/staging/res/mipmap-*/ic_launcher.png    # e.g. an amber band
android/app/src/main/res/mipmap-*/ic_launcher.png       # production
```

Same for the per-flavor `google-services.json`:
`android/app/src/<flavor>/google-services.json`. A single shared file means the QA build
reports crashes and analytics into the production project — which is worse than no data,
because it makes the production numbers wrong.

| Flavor | applicationId | Label | Firebase project |
|---|---|---|---|
| `dev` | `com.example.app.dev` | Example Dev | `example-dev` |
| `staging` | `com.example.app.staging` | Example QA | `example-staging` |
| `prod` | `com.example.app` | Example | `example-prod` |

**The suffix goes on non-production flavors only.** Suffixing production changes the
application id of a live app, which the store treats as a different app entirely — a new
listing, no upgrade path, and every existing install stranded.

**Rule: the deep-link and OAuth redirect registrations follow the suffixed id.** Anything
keyed on the application id — App Links fingerprints, an OAuth `redirect_uri` scheme, a
Facebook/Google client id — needs a per-flavor entry. A staging build with the production
`assetlinks.json` fingerprint fails link verification with no error surface. Registration of
those files is `frontend/go-router`.

## 5. iOS flavors: schemes, configurations, bundle-id suffix

iOS has no `productFlavors`. `--flavor prod` maps to an **Xcode scheme** named `prod`, and
that scheme's build configurations carry the per-flavor values. The mechanism differs; the
three requirements — distinct bundle id, distinct display name, distinct icon — do not.

**Rule: one scheme per flavor, and one build configuration per (flavor × Debug/Release/Profile)
pair.** Flutter looks for a configuration whose name contains the flavor name.

```
Schemes:          dev            staging            prod
Configurations:   Debug-dev      Debug-staging      Debug-prod
                  Release-dev    Release-staging    Release-prod
                  Profile-dev    Profile-staging    Profile-prod
```

**Rule: the per-flavor values live in `.xcconfig` files, not in `project.pbxproj`.** A value
typed into the Xcode UI lands in `project.pbxproj` as a build setting duplicated per
configuration, which is unreviewable in a diff and is the file most likely to conflict on
merge. An `.xcconfig` is three readable lines.

```
// ios/Flutter/Release-staging.xcconfig
#include "Generated.xcconfig"
#include "Pods/Target Support Files/Pods-Runner/Pods-Runner.release.xcconfig"

PRODUCT_BUNDLE_IDENTIFIER = com.example.app.staging
PRODUCT_NAME = Example QA
DISPLAY_NAME = Example QA
ASSETCATALOG_COMPILER_APPICON_NAME = AppIcon-staging
IPHONEOS_DEPLOYMENT_TARGET = 14.0
```

**Rule: `Info.plist` references the build setting; it never hardcodes the name or id.**

```xml
<!-- ios/Runner/Info.plist -->
<key>CFBundleDisplayName</key>
<string>$(DISPLAY_NAME)</string>
<key>CFBundleIdentifier</key>
<string>$(PRODUCT_BUNDLE_IDENTIFIER)</string>
```

A literal in `Info.plist` overrides the configuration, and every flavor installs under the
same bundle id — the iOS version of the shared-label bug in §4, with the additional
consequence that TestFlight and the App Store see them as one app.

**Per-flavor `GoogleService-Info.plist`** goes in `ios/config/<flavor>/`, copied into the
bundle by a run-script build phase keyed on `$CONFIGURATION`. A single shared file has the
same consequence as on Android.

| Concern | Android | iOS |
|---|---|---|
| Flavor selector | `productFlavors` | Scheme + build configuration |
| Id suffix | `applicationIdSuffix` | `PRODUCT_BUNDLE_IDENTIFIER` per `.xcconfig` |
| Display name | `resValue("string", "app_name", …)` | `DISPLAY_NAME` → `$(DISPLAY_NAME)` in `Info.plist` |
| Icon | `src/<flavor>/res/mipmap-*` | `ASSETCATALOG_COMPILER_APPICON_NAME` |
| Min OS | `minSdk` | `IPHONEOS_DEPLOYMENT_TARGET` |

**Rule: the entitlements file is per-configuration too.** Associated domains, push
environment (`development` vs `production` APNs) and keychain access groups all key on the
bundle id. One shared `.entitlements` means the staging build claims the production
associated domain, and universal links resolve to whichever app iOS picked.

## 6. Explicit API levels and the pinned toolchain

**Rule: `minSdk`, `targetSdk`, `compileSdk` and `IPHONEOS_DEPLOYMENT_TARGET` are literal
integers in the repo. Never `flutter.minSdkVersion`, `flutter.targetSdkVersion` or
`flutter.compileSdkVersion`.**

Those properties are supplied by whatever Flutter SDK is running the build. Upgrading Flutter
therefore changes the set of devices your app supports — silently, in a commit whose diff is
one line in `.fvmrc`. A `minSdk` bump drops every device below the new floor out of the store
listing; users on those devices stop receiving updates and never see an error. A `targetSdk`
bump opts you into a year of new platform behaviour changes (background restrictions, storage
scoping, permission prompts) with no code review.

```kotlin
// ✅ explicit — changing the device floor is a reviewable one-line diff
minSdk = 24
targetSdk = 35
compileSdk = 35
```

```kotlin
// ❌ the values move when the toolchain moves
minSdk = flutter.minSdkVersion
targetSdk = flutter.targetSdkVersion
compileSdk = flutter.compileSdkVersion
```

The same argument applies to `IPHONEOS_DEPLOYMENT_TARGET`: set it in the `.xcconfig` **and**
in the `Podfile` `platform :ios, '14.0'` line, because a mismatch produces pods built for a
different floor than the app.

**Rule: every tool version is pinned in a file in the repo, and CI reads that file.**

| Tool | Pinned in | Read by CI as |
|---|---|---|
| Flutter / Dart | `.fvmrc` | `flutter-version-file: .fvmrc` |
| JDK | `.tool-versions` or the workflow's `java-version` | `actions/setup-java` with an exact `17` |
| Xcode | `.xcode-version` | `sudo xcode-select -s /Applications/Xcode_16.2.app` |
| CocoaPods | `Gemfile` + `Gemfile.lock` | `bundle exec pod install` |
| Gradle | `gradle/wrapper/gradle-wrapper.properties` | the checked-in `./gradlew` |
| Ruby (fastlane) | `.ruby-version` + `Gemfile.lock` | `ruby/setup-ruby` with `bundler-cache: true` |

```json
// .fvmrc
{ "flutter": "3.32.0" }
```

```yaml
- uses: subosito/flutter-action@v2
  with:
    flutter-version-file: .fvmrc     # not a hardcoded number
    cache: true
```

**The number is written once.** A workflow that restates `flutter-version: 3.32.0` next to a
`.fvmrc` saying something else is the most common source of "it builds on my machine": the
developer is on the `.fvmrc` version, CI is on the workflow's, and the disagreement surfaces
as a codegen diff or an analyzer error nobody can reproduce.

**Rule: `pod install` runs through `bundle exec`, and `Podfile.lock` and `Gemfile.lock` are
committed.** An unpinned CocoaPods resolves different pod versions on two consecutive runs of
the same commit, which makes a red build unreproducible.

## 7. The PR gate: four checks, Linux, under ten minutes

**Rule: exactly four checks are required to merge, they all run on Linux, and the whole gate
finishes in under ten minutes.**

```yaml
# .github/workflows/pr.yml
name: PR
on:
  pull_request:
    branches: [main]

concurrency:
  group: pr-${{ github.head_ref }}
  cancel-in-progress: true

jobs:
  gate:
    runs-on: ubuntu-24.04
    timeout-minutes: 10
    steps:
      - uses: actions/checkout@v4

      - uses: subosito/flutter-action@v2
        with:
          flutter-version-file: .fvmrc
          cache: true

      - name: Resolve dependencies from the lockfile
        run: flutter pub get --enforce-lockfile

      - name: Format
        run: dart format --output=none --set-exit-if-changed .

      - name: Analyze
        run: flutter analyze --fatal-infos --fatal-warnings

      - name: Test
        run: flutter test --coverage
```

| Check | Command | What it stops |
|---|---|---|
| Format | `dart format --output=none --set-exit-if-changed .` | Whitespace churn in every future diff |
| Analyze | `flutter analyze --fatal-infos --fatal-warnings` | Every lint in §8, at the severity §8 declares |
| Test | `flutter test --coverage` | The obvious one |
| Resolution | `flutter pub get --enforce-lockfile` | A transitive upgrade nobody reviewed |

**`--fatal-infos` is the load-bearing flag.** Most lints — including `prefer_const_constructors`
and the majority of `flutter_lints` — report at **info** severity. `flutter analyze` with no
flags exits `0` on info-level diagnostics. So a repository with a carefully tuned
`analysis_options.yaml`, a green gate, and hundreds of violations is the normal state of
affairs, and the config is decorative. `--fatal-infos` is what converts the file into a gate.
`--fatal-warnings` is redundant in recent SDKs but harmless, and explicit is better than
version-dependent.

**`--set-exit-if-changed` is the equivalent for formatting.** `dart format .` *rewrites* the
files and exits `0`; on a CI runner that means the check reformats a throwaway checkout and
passes. `--output=none` stops the rewrite; `--set-exit-if-changed` produces the failure.

**`--enforce-lockfile` is the equivalent for dependencies.** A plain `flutter pub get` will
happily resolve a newer compatible version than `pubspec.lock` records and update the lockfile
in place, so CI tests a dependency set that no one reviewed and that the developer does not
have. With the flag, a resolution that would change the lockfile is an error.

**Rule: no iOS build in the gate.** A `flutter build ios` needs a macOS runner. On GitHub-hosted
runners a macOS minute is billed at roughly ten times a Linux minute, and the build itself is
several times slower, so a single iOS gate step can cost more than the rest of CI combined and
push the gate past ten minutes on its own. iOS builds run **on merge to `main`**, where a
failure is a revert rather than a blocked PR.

```yaml
# .github/workflows/main.yml — after merge, not in the gate
jobs:
  ios:
    runs-on: macos-14
    timeout-minutes: 40
```

**Rule: the ten-minute budget is a real constraint, kept by these five levers.**

| Lever | Effect |
|---|---|
| `cache: true` on the Flutter action | Saves the SDK download, ~1–2 min |
| `concurrency` with `cancel-in-progress` | A force-push does not leave the old run burning minutes |
| Integration and golden tests on a nightly schedule | The gate runs unit and widget tests only |
| Codegen diffed, not regenerated from scratch (§9) | `build_runner` on a warm cache, not `--delete-conflicting-outputs` |
| One job, not four | Four jobs pay the checkout + SDK setup cost four times |

A gate over ten minutes stops being a gate: people open the PR, switch tasks, and merge on a
green tick they did not watch. The number matters more than which checks you drop to hit it.

**Rule: the four checks are configured as *required* status checks on the branch, and the
branch is protected.** A check that can be merged past is a linter with extra steps.

## 8. `analysis_options.yaml` — the canonical file

**This layer owns the file.** Other layers reference individual settings from it —
`language/dart-models` requires `strict-casts` and the freezed exception,
`logging/flutter-observability` requires `avoid_print` at error severity,
`frontend/flutter-ui` requires `use_build_context_synchronously` at error severity and
`prefer_const_constructors`. The file below is the union. Do not maintain a second copy.

```yaml
# analysis_options.yaml
include: package:flutter_lints/flutter.yaml

analyzer:
  language:
    strict-casts: true
    strict-inference: true
    strict-raw-types: true

  errors:
    # freezed places @JsonKey and converters on factory parameters
    invalid_annotation_target: ignore
    # promoted from info/warning — these are correctness bugs, not style
    use_build_context_synchronously: error
    avoid_print: error
    unawaited_futures: error
    # `--fatal-infos` (§7) makes info fatal, so a TODO must be ignored, not demoted
    todo: ignore

  exclude:
    - "**/*.freezed.dart"
    - "**/*.g.dart"
    - "**/*.gr.dart"
    - "**/*.mocks.dart"
    - "lib/l10n/generated/**"

linter:
  rules:
    always_use_package_imports: true
    avoid_print: true
    prefer_const_constructors: true
    prefer_const_literals_to_create_immutables: true
    use_key_in_widget_constructors: true
    use_super_parameters: true
    unawaited_futures: true
    avoid_dynamic_calls: true
    cancel_subscriptions: true
    close_sinks: true
```

**Do not add `require_trailing_commas`.** It was removed from the linter once the tall-style
formatter stopped treating a trailing comma as a layout instruction. An unrecognised rule name
is itself a diagnostic, and under `--fatal-infos` (§7) that fails the gate — so a stale lint
list breaks the build it was meant to protect. Check a rule still exists before adding it.

Why each of the non-obvious ones is here:

| Setting | Reason |
|---|---|
| `strict-casts` | The implicit downcast from a JSON `dynamic` is accepted without it, so "no unchecked casts" is unenforceable by review — `language/dart-models` §2 |
| `strict-inference` | A parameter inferred as `dynamic` disables every other check downstream of it |
| `strict-raw-types` | A bare `List` or `Future` silently becomes `List<dynamic>` |
| `use_build_context_synchronously: error` | Using a `BuildContext` after an `await` crashes only on a slow network, so it ships — `frontend/flutter-ui` §6 |
| `avoid_print: error` | `print` writes to the platform log in release; the message is often a response body — `logging/flutter-observability` §3 |
| `always_use_package_imports` | A relative import that crosses a feature boundary hides the dependency from review, and breaks when the file moves |
| `unawaited_futures: error` | An unawaited future's error is uncaught and reaches `PlatformDispatcher.onError`, or nothing at all |
| `prefer_const_constructors` | A non-const leaf in a `ListView.builder` rebuilds a subtree per frame — `frontend/flutter-ui` §8 |
| `invalid_annotation_target: ignore` | Not a style choice: freezed's own generated pattern trips it, so without this the file cannot be clean |

**Rule: `always_use_package_imports` and `prefer_relative_imports` are mutually exclusive.**
Enable exactly one, project-wide. This layer's answer is package imports. Enabling both makes
every import in the project a violation of one of them, and the usual reaction is to disable
the analyzer rather than pick.

**Rule: severity is declared under `analyzer.errors`, not implied by the lint list.** A lint
listed under `linter.rules` reports at its *default* severity — for most rules, info. With
`--fatal-infos` in the gate that is already fatal, but the promotion to `error` is what makes
the rule fatal in the IDE too, where the developer sees it eight hours earlier.

**Rule: `exclude` covers generated files, and generated files only.** Excluding a hand-written
directory to get to green hides that directory from every check in §7 permanently, and nothing
in the build ever mentions it again.

**Rule: the ban on `debugPrint` needs a grep, because no lint covers it.** `avoid_print`
catches `print` only. Add it to the gate as a fifth non-blocking-to-write, blocking-to-merge
step:

```yaml
- name: No print or debugPrint in lib/
  run: |
    ! grep -rn --include='*.dart' -E '(^|[^A-Za-z0-9_])(print|debugPrint)\(' lib/
```

## 9. CI asserts its own inputs

**Rule: before anything is built, CI verifies each input it depends on and fails with a
message naming the missing thing.**

A missing secret does not present as "missing secret". It presents as an empty file, which
presents as a `String.fromEnvironment` returning empty, which presents as a null-check failure
in an unrelated widget forty seconds into the build — or, worse, as a successful build of an
app pointed at nothing. The five minutes spent on assertions is repaid the first time.

```yaml
- name: Write env file
  env:
    ENV_STAGING_B64: ${{ secrets.ENV_STAGING_B64 }}
  run: |
    printf '%s' "$ENV_STAGING_B64" | base64 -d > .env_staging

- name: Assert env file is present and non-empty
  run: |
    if [ ! -s .env_staging ]; then
      echo "::error::.env_staging is empty — secret ENV_STAGING_B64 is unset or not valid base64"
      exit 1
    fi
    # FLAVOR is not in here — it stays on the command line, next to --flavor (§1)
    for key in API_BASE_URL IDENTITY_POOL_ID; do
      grep -q "^$key=" .env_staging || {
        echo "::error::.env_staging is missing $key"
        exit 1
      }
    done
```

Note what is asserted and what is not: the file is non-empty, and every key the app reads is
present **by name**. The values are never printed. `[ -s <file> ]` is the whole check — it is
one bracket expression, and it converts the most common CI failure in a mobile repo from a
twenty-minute bisect into a one-line error at second thirty.

**Rule: codegen output is regenerated and diffed, never assumed.**

```yaml
- name: Codegen is up to date
  run: |
    dart run build_runner build --delete-conflicting-outputs
    git diff --exit-code -- '*.g.dart' '*.freezed.dart' 'lib/l10n/'
```

`git diff --exit-code` is the assertion. Without it there are two failure modes, and the gate
catches neither: a developer edits a model and forgets to regenerate, so `main` compiles
against stale generated code that happens to still be valid; or a developer hand-edits a
generated file, and the change vanishes for whoever next runs the generator.

The diff must be scoped to generated paths. An unscoped `git diff --exit-code` also fails on
the `.env_staging` you just wrote and on anything the SDK setup touched, so it gets deleted
after the second false failure.

**Rule: a check that can be skipped is not a check.** No `continue-on-error`, no `|| true`, no
`if: always()` on an assertion step. Every one of those has the same effect as deleting the
step, with the added cost that a red X somewhere in the log makes people stop reading logs.

**Assertion checklist for the release path:**

| Assert | How |
|---|---|
| Env file non-empty and complete | `[ -s .env_<flavor> ]` plus a `grep -q "^KEY="` per key |
| Codegen current | `git diff --exit-code` on generated paths |
| Lockfile respected | `flutter pub get --enforce-lockfile` (§7) |
| The flavor is one of the known three | `case "$FLAVOR" in dev\|staging\|prod) ;; *) exit 1 ;; esac` |
| Signing material decoded | `[ -s upload-keystore.jks ]` after `base64 -d` |
| Build number is higher than the last upload | §10 |

## 10. Versioning: generated by CI, monotonic

**Rule: the build number is generated by CI, is strictly increasing, and is never edited by
hand. Nothing is built or uploaded from a developer machine.**

Both stores reject a build whose number is not higher than one already uploaded — after the
upload, at the end of a twenty-minute pipeline. A hand-maintained `version:` line in
`pubspec.yaml` collides the first time two branches merge in the same afternoon, and a
developer-machine build has an unknown Flutter version, unknown dependency versions, unreviewed
local edits, and no record of what went in it.

```yaml
- name: Compute version
  id: version
  run: |
    VERSION_NAME=$(grep '^version:' pubspec.yaml | sed 's/version: *//' | cut -d+ -f1)
    BUILD_NUMBER=${{ github.run_number }}
    echo "name=$VERSION_NAME" >> "$GITHUB_OUTPUT"
    echo "number=$BUILD_NUMBER" >> "$GITHUB_OUTPUT"

- name: Build
  run: |
    flutter build appbundle --release \
      --flavor prod \
      --dart-define=FLAVOR=prod \
      --build-name=${{ steps.version.outputs.name }} \
      --build-number=${{ steps.version.outputs.number }}
```

| Source for the build number | Monotonic? | Verdict |
|---|---|---|
| `github.run_number` | Yes, per workflow | ✅ the default choice |
| Unix timestamp (`date +%s` / `%y%m%d%H%M`) | Yes | ✅ but check the 2,100,000,000 `versionCode` ceiling |
| `git rev-list --count HEAD` | Only on a linear history | ⚠️ a squash-merge history is fine; a rebase-and-force is not |
| Short commit SHA | No | ❌ not an integer, not ordered |
| Hand-edited `pubspec.yaml` | No | ❌ collides on merge |

**Rule: the version *name* comes from `pubspec.yaml` and is bumped in a reviewed commit; the
build *number* comes from CI.** They answer different questions — the name is the release the
user sees, the number is the artefact. Deriving one from the other loses one of them.

**Rule: the same build number reaches the crash reporter.** `packageInfo.buildNumber` is set
as a crash key at bootstrap (§3). A crash report you cannot map to an artefact cannot be
symbolicated, which makes §11 pointless.

**Rule: the release tag, the artefact, and the symbol upload all carry the same
`<name>+<number>`.** One string, computed once in one step, referenced everywhere. Recomputing
it in the upload job is how the symbols end up filed under a build that does not exist.

## 11. The release job: obfuscate and upload symbols together

**Rule: `--obfuscate` and `--split-debug-info` are always passed together, and the symbol
directory is uploaded in the same job that produced it.**

`--obfuscate` renames every Dart class, method and field in the release binary. That is the
point — it raises the cost of reverse-engineering the app. It also means every stack trace the
crash reporter receives is a list of names like `bnA.k7`. The `--split-debug-info` output is
the only thing that maps those back. Ship one without the other and you have traded a readable
binary for unreadable crash reports, which is a strictly worse position than not obfuscating
at all.

```yaml
  release-android:
    runs-on: ubuntu-24.04
    timeout-minutes: 30
    steps:
      # … checkout, flutter setup, env assertions (§9), version (§10) …

      - name: Build App Bundle
        run: |
          flutter build appbundle --release \
            --flavor prod \
            --dart-define=FLAVOR=prod \
            --dart-define-from-file=.env_prod \
            --build-name=${{ steps.version.outputs.name }} \
            --build-number=${{ steps.version.outputs.number }} \
            --obfuscate \
            --split-debug-info=build/symbols/prod

      - name: Upload Dart symbols
        uses: actions/upload-artifact@v4
        with:
          name: symbols-prod-${{ steps.version.outputs.number }}
          path: build/symbols/prod
          retention-days: 90
          if-no-files-found: error

      - name: Upload native symbols to the crash reporter
        run: |
          ./scripts/upload-symbols.sh \
            --flavor prod \
            --build-number ${{ steps.version.outputs.number }}
```

Three details that are not decoration:

- **`if-no-files-found: error`.** Without it, a build that silently produced no symbols
  uploads an empty artefact and the job is green. That is the exact failure this rule exists
  to prevent, so it must be fatal.
- **Same job.** The symbol directory is inside the runner's workspace and disappears when the
  job ends. A "upload symbols" job scheduled later has nothing to upload unless you pass the
  directory through as an artefact — at which point you have two chances to get it wrong.
- **Retention outlives the release.** Ninety days is a minimum: a crash arrives from a user
  who has not updated in two months, and a seven-day retention makes it unreadable.

**Rule: the native symbols go up too.** `--split-debug-info` covers the Dart side only.
Android needs the debug symbols for the NDK libraries (`build/app/intermediates/merged_native_libs`
or the `symbols` output of the bundle), and iOS needs the dSYMs from the archive. Flutter's
engine frames are native.

**Rule: a release build is `--release`, never `--profile`, and never has a debug signing
config.** A `--profile` build ships the observatory and the timeline, both of which are remote
inspection surfaces.

**Rule: the release job runs from a tag or from `main`, with an environment that requires
approval.** `environment: production` on the job gives you the approval gate, the deployment
record and the scoped secrets for free.

## 12. Runners and secrets

**Rule: every runner image is pinned to a dated label.**

```yaml
runs-on: ubuntu-24.04     # ✅ pinned
runs-on: macos-14         # ✅ pinned
```

The floating alias is repointed by the provider on their schedule, which means the JDK, the
Xcode version, the CocoaPods version and the preinstalled Android SDK components change under
a commit that has not changed. A build that was green last week fails today with no diff, and
the whole §6 pinning exercise is undone by the one line that decides which machine reads those
pins.

**Rule: every third-party action is pinned to a tag at minimum, and to a commit SHA for
anything that touches secrets.** An action referenced by a moving branch is arbitrary code
execution with access to whatever that job can read.

```yaml
- uses: actions/checkout@v4                                    # ✅ tag
- uses: some-org/deploy@3f7a1e2c9b4d5e6f7a8b9c0d1e2f3a4b5c6d7e8f   # ✅ SHA for a secret-reading step
```

**Rule: a secret reaches a command through the environment or a file, never through string
interpolation into a `run:` body.**

```yaml
# ✅ the value arrives as an env var; the log shows the variable name
- name: Decode keystore
  env:
    KEYSTORE_B64: ${{ secrets.ANDROID_KEYSTORE_B64 }}
  run: |
    printf '%s' "$KEYSTORE_B64" | base64 -d > android/upload-keystore.jks
    [ -s android/upload-keystore.jks ] || { echo "::error::keystore decode failed"; exit 1; }
```

Interpolating `${{ secrets.X }}` directly into a `run:` body substitutes the value into the
script *before* the shell sees it. The masker still redacts it from the log, but the value is
now in the process command line — visible to `ps`, and to any `set -x` in the same script.

**Why base64 for anything binary or multiline.** A keystore is binary; an `.env` file and a
`.p8` key are multiline. Both survive a secret store, and neither survives being echoed
through a shell that mangles newlines. `base64 -d` is the decode step; it also means the secret
as stored is a single line with no shell metacharacters.

**Never do these:**

| Anti-pattern | Consequence |
|---|---|
| `echo "$SECRET"` to "check it's set" | The masker covers exact matches only — an echo of a substring, or of a base64 of it, is printed |
| `set -x` in a step handling secrets | Every expansion is traced to the log, masking included |
| Secrets in a `pull_request_target` workflow | Runs with the base repo's secrets against a fork's code |
| A secret as a build argument in a Docker image | Persists in a layer |
| `--dart-define=API_KEY=…` for a real secret | Compiled into the binary in plaintext; extractable with `strings` |

That last one deserves its own line. **`--dart-define` is configuration, not a secret store.**
A base URL, a pool id, a public client id — fine. An API key, a signing secret, a database
password — never: it is embedded verbatim in the shipped binary. The same rule appears in
`storage/flutter-local` for database encryption keys, and for the same reason.

**Rule: `permissions:` is declared at the workflow level and is least-privilege.**

```yaml
permissions:
  contents: read      # raise per-job only where a job needs more
```

## 13. Common mistakes

| Mistake | Why it hurts | Instead |
|---|---|---|
| `--flavor prod` with no `--dart-define=FLAVOR=prod` | Production binary, dev backend, dev identity pool, nothing looks wrong | Both switches, from one input (§1) |
| A fallback value on `String.fromEnvironment('FLAVOR')` | A forgotten define compiles and boots as the fallback | No fallback; throw on empty (§2) |
| `FLAVOR` inside `.env_<flavor>` instead of on the command line | A file mix-up becomes undetectable | Keep `FLAVOR` next to `--flavor` (§1) |
| An unknown flavor name falling back to dev | Reintroduces the same bug via a typo | Throw on unrecognised (§2) |
| Flavor known only in Dart, never surfaced | "Which build is this?" needs a rebuild to answer | Log line + crash keys + banner (§3) |
| No `applicationIdSuffix` on non-production flavors | QA build overwrites production on the device | Suffix every non-prod flavor (§4) |
| `android:label` hardcoded in the shared manifest | Overrides every per-flavor `resValue`; all flavors named alike | `@string/app_name` (§4) |
| One shared `google-services.json` | QA crashes and analytics land in the production project | Per-flavor source set (§4) |
| Bundle id typed into `project.pbxproj` | Unreviewable diff, merge conflicts, silently one bundle id | `.xcconfig` per configuration (§5) |
| `minSdk = flutter.minSdkVersion` | A Flutter upgrade changes supported devices with no diff | Explicit integers (§6) |
| Flutter version in both `.fvmrc` and the workflow | They drift; "works on my machine" | `flutter-version-file: .fvmrc` (§6) |
| `flutter analyze` with no flags | Info-level lints pass; `analysis_options.yaml` is decorative | `--fatal-infos --fatal-warnings` (§7) |
| `dart format .` as the check | Rewrites the checkout and exits 0 | `--output=none --set-exit-if-changed` (§7) |
| `flutter pub get` in CI | Silently resolves past the lockfile | `--enforce-lockfile` (§7) |
| An iOS build inside the PR gate | ~10× the cost per minute, and blows the ten-minute budget | Build iOS on merge (§7) |
| Both `always_use_package_imports` and `prefer_relative_imports` | Every import violates one of them; the analyzer gets disabled | Pick one — package imports (§8) |
| Excluding a hand-written directory from the analyzer | Permanently invisible to every check | Exclude generated paths only (§8) |
| Trusting `avoid_print` to catch `debugPrint` | `debugPrint` writes to the platform log in release | Add the grep step (§8) |
| Building before checking the env file | A missing secret surfaces as an unrelated error minutes later | `[ -s .env_<flavor> ]` first (§9) |
| Running `build_runner` without diffing | Stale or hand-edited generated code reaches `main` | `git diff --exit-code` on generated paths (§9) |
| `continue-on-error` on an assertion | Identical to deleting the step, and teaches people to ignore red | Let it fail (§9) |
| Build number from a commit SHA or hand-edited | Not monotonic; the store rejects at upload | `github.run_number` (§10) |
| A release built on a developer machine | Unknown toolchain, unreviewed local edits, no record | CI only (§10) |
| `--obfuscate` without `--split-debug-info` upload | Every crash report is unreadable forever | Both, same job, `if-no-files-found: error` (§11) |
| Symbols uploaded from a later job | The directory is gone with the runner | Same job (§11) |
| `runs-on: ubuntu-latest` | The toolchain moves under an unchanged commit | Dated label (§12) |
| `${{ secrets.X }}` interpolated into a `run:` body | The value lands in the process command line | Pass via `env:` (§12) |
| `echo "$SECRET"` to verify it is set | Masking covers exact matches only | Assert with `[ -s <file> ]` (§9, §12) |
| A real API key via `--dart-define` | Plaintext in the shipped binary | Server-side; `--dart-define` is config only (§12) |
