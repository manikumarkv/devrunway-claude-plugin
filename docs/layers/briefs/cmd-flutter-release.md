# Brief — `/flutter-release`

**Kind:** slash command (`skills/flutter-release/`) · **Issue:** #2 · **Cookbook:** `#release`

`user-invocable: true`. Sub-commands: `plan`, `cut`, `watch`, `hotfix`.

## Content to encode
1. **You cannot roll back a mobile release.** Users who updated stay updated. Everything
   below follows from that single fact, and it is the thing teams from a web background get
   wrong on their first bad release.
2. **Incident order, with time-to-effect:**

   | Order | Action | Effect |
   |---|---|---|
   | 1 | Halt the staged rollout | Minutes — stops *new* users receiving it |
   | 2 | Kill switch the feature, or fix server-side | Minutes — reaches users already updated |
   | 3 | Ship a fix and roll forward | Hours to days, plus review |
   | 4 | Force update | Blunt; every user pays for one cohort's bug |

   Steps 1 and 2 are why the flags layer is infrastructure. A team without a kill switch has
   only step 3, and step 3 takes a day at best.
3. Trunk-based with short-lived branches. A release cut is a tag; a release branch exists
   only while a hotfix needs it, and the hotfix merges back to trunk the same day — never
   fixed only on the branch.
4. A fixed cadence beats releasing when something is ready. Predictability is what lets you
   skip a release calmly when quality is not there.
5. Version follows a stated scheme; the build number is generated by CI and monotonic across
   all flavors and both platforms.
6. **Halt criteria written down before the release**, with numbers and an owner watching:
   crash-free-users delta, a new signature entering the top five, funnel completion drop, ANR
   threshold — each evaluated only at meaningful adoption and elapsed time. Deciding whether
   a number is bad while watching it climb produces the wrong answer every time.
7. Production is a **promotion** of the artifact testers used, never a rebuild. A rebuild is
   a different binary that nobody tested.
8. Release notes generated from the repo — a changelog section or the commits since the last
   tag — so store text and code cannot disagree.
9. Every release is tagged, and the tag maps to an artifact and a symbol file that still exist.
10. Forced update is reserved for genuine incompatibility — a security fix or a broken API
    contract — not for encouraging adoption.
11. A short written post-release check at a set time after every rollout: crash rate, funnel,
    store reviews. Not only when something feels wrong.

## Acceptance
- [ ] `plan` emits halt criteria with concrete numbers, an adoption floor, and a named owner
- [ ] `hotfix` branches from the released tag and reminds to merge back to trunk
- [ ] Never offers "roll back the release" as an option
- [ ] `watch` distinguishes crash-free users from crash-free sessions
